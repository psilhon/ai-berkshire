三、关键发现

发现 1：workbuddy-skills 是 canonical 的原样镜像（非独立适配层）

证据

  • diff skills/full-company-analysis-workbuddy.md workbuddy-skills/full-company-analysis-workbuddy/SKILL.md → IDENTICAL（10481 字节完全一致）
  • 而 codex-skills/full-company-analysis-workbuddy/SKILL.md 为 11699 字节（多了 Codex adapter note）——codex 版是转换版，workbuddy 版是纯镜像
  • tests/test_workbuddy_adapter.py 第 45-54 行硬断言：test_adapter_is_exact_copy_of_canonical_workflow 要求字节级相等

结论：workbuddy-skills 目录的存在意义 = 为 WorkBuddy 提供一个「按 canonical 原样同步的生产适配器」，与 codex 的「adapter note 转换版」刻意区分。

发现 2：codex-skills 全部 17 个生成包均有对应源，无孤儿

  • 17 个 codex-skills/*/ 目录 ↔ skills/*.md 一一对应（已逐一核验）
  • 仅 investment-memo-craft 无 skills/ 同名源 —— 符合 AGENTS.md 约定（Codex-only 手写包，明确标注，不得创建同名源）
  • investment-memo-craft/agents/openai.yaml 是唯一的附属资产（v3.4.14 曾因漏复制该资产触发 P1 修复）

发现 3：skills/ 混入 2 个非 skill 辅助文件

四、合并优化方案

方案 A（推荐）：保持「单源双镜像」架构，只做微清理

理由

三目录架构是刻意的「单源多目标」设计：skills/ 手写 → codex-skills/ 转换版（adapter note）+ workbuddy-skills/ 原样版。两者消费方不同（Codex 线程 vs WorkBuddy 生产），且各有守卫测试钉死（test_workbuddy_adapter / check.sh 同步校验）。不建议物理合并——合并 codex/workbuddy 会让 WorkBuddy 侧被迫吞下 Codex adapter note，或让 Codex 侧丢失平台适配说明。

执行项：

  • ✅ 清理 skills/ashare-data.test-prompts.json（零引用一次性产物，可删或移入 local/darwin-evaluation/ 同类目录）
  • ✅ 文档补一句三目录关系说明（本报告即载体，可选同步进 CLAUDE.md）
  • ✅ 零脚本改动、零测试改动，check.sh 不受影响

方案 B（可选优化）：sync 脚本去重 workbuddy 复制路径

说明

sync-codex-skills.py 中 workbuddy 复制是独立分支（122-129 行），与 codex 生成共用循环但目标路径不同。可微调：把 workbuddy 复制并入统一「生成目标」循环，减少分支代码。但收益极小（脚本仅 150 行、逻辑已清晰），不推荐为重构而重构。

方案 C（不推荐）：合并三目录为单一 skills/

风险

  • 破坏 tests/test_workbuddy_adapter.py 路径硬依赖（ADAPTER 常量指向 workbuddy-skills/）
  • 破坏 tests/test_full_analysis_docs.py ACTIVE_DOCS 列表（含 workbuddy-skills 路径）
  • 破坏 tests/test_deploy_user_skills.py / test_install_scripts.py（按 codex-skills 目录部署）
  • README/CLAUDE.md 多处链接失效

结论：三目录是被测试与文档「钉死」的既定契约，合并将引发连锁改动且无实质收益。
